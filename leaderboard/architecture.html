Stage 01 · Entrypoints & Phase Triggers

serve.py · aws_alpha.py · aws_worker.py

Local Workstation (local)

Loopback dev server (127.0.0.1:8765) with the run.html Terminal launcher and mint LOCAL header badge.

python -m leaderboard.serve --phase local

DAPLab AWS Staging (alpha)

Uses one fixed-size t3a.xlarge in us-east-1. It defaults to On-Demand capacity, a 64 GiB encrypted root disk, and private S3. The CLI verifies the shared account ID and IAM username. Alpha timings are not ranked.

aws_alpha.sh run --daplab-project <project> --owner <uni> --daplab-account-id <account> --collapse-after

Official Cloud Target (prod)

The planned launcher assigns one On-Demand m7a.2xlarge to each self-hosted database. Each worker has a dedicated 200 GiB gp3 data volume. Workers may run concurrently. Each worker runs Microbench and Macrobench sequentially.

worker command: aws_worker.sh --systems <db> --machine <id> --preset full

Stage 02 · Mutual Exclusion, Alpha Lease & Provenance Snapshot

leaderboard/.runs/

Hardware & Lease Locks

Acquires non-blocking flock on batch.lock and run.lock and verifies alpha.owner so two runs never share CPU, RAM, or NVMe.

leaderboard/.runs/{alpha,batch,run}.lock

Crash-Recovery Journals

Persists active DB names before server start. If a run is killed by SIGKILL, the next invocation replays teardown before starting.

leaderboard/.runs/<system>.{journal,active}.json

Git & Execution Profile

Captures source_snapshot(CODE_PATHS), suite_sha256, and execution_profile (local_single_host, economic_single_vm, or paper_separated_vms).

source_snapshot() · execution_profile

Stage 03 · Three Benchmark Execution Lanes

run.py · run_macro.py · verbs.py

3A · MICROBENCH LANE

Seeds the CH-benCHmark dataset and times 8 isolated operations across 3 independent tries on fresh bb_<id> databases.

python -m leaderboard.run <system> --machine <id>

3B · MACROBENCH LANE (S1–S6)

Executes 6 stateful agent workflows in isolated subprocesses, supporting both Full-suite and --native-only campaign modes.

python -m leaderboard.run_macro <system> --preset full --machine <id>

3C · VERB SCALING LANE (S0_verbs)

Sweeps fanout, depth, mutation_scale, and concurrency in isolated process groups with verified cleanup.

python -m leaderboard.verbs <system> --machine <id>

Stage 04 · System Integrations & dblib Connectors

leaderboard/systems/<system>/

Self-Hosted Engines

Dolt, Doltgres, MatrixOne, SeekDB, PostgreSQL FILE_COPY, and Chronos keep metadata, connector code, and executable lifecycle hooks inside leaderboard/systems/<system>/.

install → start → check → CONNECTOR → stop

Managed Cloud Services

Each hosted manifest declares public credential variable names. The runnable Neon and Xata connectors call preflight() and record SQL round-trip latency (rtt_ms). Tiger Cloud remains metadata-only.

--client-location <loc> · rtt_ms probe

Production Compute Placement

The current policy assigns m7a.2xlarge and the same gp3 profile to every database. A future per-database map may override it. Different profiles must use separate hardware cohorts.

current: m7a.2xlarge + gp3 · future key: database

3. Benchmark Suites & Cohort Separation

BranchBench evaluates database branching across three complementary suites while strictly isolating hardware and campaign cohorts.

Agent Workflows (S1–S6)
Six stateful AI agent scenarios (rl_env, context_mgmt, multi_agent, dev_agent, ops_agent, data_agent) exercising nine Git-like verbs alongside concurrent SQL queries. Supports both Full-suite and --native-only campaign modes.
Operations (Micro)
Eight isolated operations (time_to_first_query, branch_create, branch_connect, read, range_read, insert, update, range_update) plus load_time and provision_time on a deterministic CH-benCHmark seed (leaderboard/suite.json).
Verb Scaling (S0_verbs)
Controlled micro-suite sweeping fanout, depth, mutation_scale, and concurrency via python -m leaderboard.verbs <system> --machine <id>.
Hardware Cohorts
Every artifact records execution_profile and only competes inside its matching profile group. The production target uses one fixed compute and storage profile. Per-database profiles require instance and volume provenance plus separate ranking groups before activation.

4. Phase Guide: local · alpha · prod

All three phases run the exact same runners and validators; the phase controls only hardware target, record selection, and UI affordances.

Local Dev (local)
python -m leaderboard.serve --phase local serves http://127.0.0.1:8765/ with the run.html launcher and mint LOCAL badge, combining local runs with leaderboard.mock reference rows.
AWS Alpha (alpha)
./leaderboard/aws_alpha.sh {up,run,deploy-site,status,collapse} requires the registered project tag, owner billing-tag1, and expected DAPLab account ID. The alpha environment is locked to us-east-1. Resource names follow {project}-{owner}-{purpose}. The worker stages git-tracked sources, retains lease ownership through artifact download, and tears down only resources with matching ownership tags.
Official Cloud (prod)
The production site already publishes only allowlisted records that pass full validation and belong to a homogeneous cohort. The planned fleet launcher will run each self-hosted database on its own On-Demand m7a.2xlarge with a 200 GiB gp3 data volume.
